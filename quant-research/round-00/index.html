Overall Progress: 0/12 Rounds
이 라운드를 먼저 읽어야 하는 이유

퀀트 리서처의 결과물은 "숫자 하나(샤프비율 1.8)"가 아니라 "그 숫자를 만든 재현 가능한 코드"다. 아무리 좋은 알파를 찾아도, 6개월 뒤에 스스로 재현하지 못하거나 동료가 검증하지 못하면 그 리서치는 존재하지 않는 것과 같다. 이 라운드에서는:

  • 리서처가 실제로 하는 일(가설 → 데이터 → 검정 → 리포트)의 루프와 13라운드 로드맵을 지도로 그린다
  • 리서치 프로젝트를 어떻게 구조화하고(data/src/notebooks/reports), 노트북을 모듈로 승격하는지 규칙을 세운다
  • Git으로 실험을 관리하고 노트북 diff 문제를 해결한다 (재현 커밋 태깅)
  • NumPy의 broadcasting·vectorization·난수 생성기를 금융 데이터 문맥에서 정확히 익힌다
  • Pandas의 Index·groupby·시계열·성능을 (date, ticker) 패널 데이터로 다룬다
  • 모든 예제는 금융 패널 데이터. shift(1)을 빼먹으면 lookahead(미래 참조)가 생기는 지점을 코드로 직접 확인한다

1. 퀀트 리서처의 하루와 이 가이드의 지도

먼저 큰 그림. 퀀트 리서처는 무엇을 하는 사람인가? 코딩만 하는 개발자도 아니고, 이론만 파는 학자도 아니다. 리서처의 일은 하나의 루프다: 시장에 대한 가설을 세우고 → 그것을 검증할 데이터를 모으고 → 통계적으로 검정하고 → 결과를 리포트로 남겨 다음 가설로 넘어간다. 이 루프를 얼마나 빠르고 정확하게, 그리고 재현 가능하게 도는지가 실력이다.

Definition 1.1 — 리서치 루프 (The Research Loop)

\[ \text{Hypothesis} \;\rightarrow\; \text{Data} \;\rightarrow\; \text{Test} \;\rightarrow\; \text{Report} \;\rightarrow\; \text{Hypothesis}' \]

↑ "가설을 세우고, 데이터를 모으고, 검정하고, 리포트로 남긴 뒤, 그 결과로 다음 가설을 다듬는 순환." 각 단계가 코드로 자동화되어 있어야 루프를 하루에 여러 번 돌 수 있다. 리서처의 생산성은 곧 이 루프의 회전 속도다.

구체적으로 하루를 그려보면 이렇다. 아침에 "저PBR 종목이 다음 달에 초과수익을 낼까?"라는 가설을 떠올린다. KOSPI200 구성 종목의 월별 재무·가격 데이터를 불러와, 매월 PBR로 5분위 포트폴리오를 만들고, 최저 분위와 최고 분위의 수익률 차이가 통계적으로 유의한지 t-검정한다. 결과 표와 누적수익 그래프를 노트북에 남기고, 커밋한다. 이 전 과정이 한 번의 클릭으로 재현되지 않으면, 다음 달 데이터가 갱신됐을 때 처음부터 다시 손으로 해야 한다. 이 라운드의 목표는 그 "한 번의 클릭"을 만드는 도구를 손에 쥐는 것이다.

학술 코드가 재현 불가능한 스파게티가 되는 근본 원인을 진단하고, 프로젝트 구조·버전 관리·테스트·환경 고정이라는 최소한의 엔지니어링 규율을 처방하는 실무 핸드북이다.

퀀트 리서치는 "학술 코드"와 "프로덕션 코드"의 최악을 동시에 안고 있다 — 탐색적이라 지저분해지기 쉬운데, 실제 돈이 걸려 있어 버그가 손실로 직결된다. 이 핸드북의 규율은 이 라운드 전체의 철학적 뼈대이며, 특히 Ch.2(구조)와 Ch.3(Git)의 근거가 된다.

핵심 정리: 리서처의 산출물은 숫자가 아니라 "그 숫자를 재현하는 코드"다. 이 라운드는 그 코드를 믿을 수 있게 만드는 도구 라운드다. 나머지 12개 라운드가 이 위에 쌓인다. 특히 Ch.6의 groupby-transform 패턴은 R5의 시그널 전처리에서 그대로 재등장한다 — 지금 몸에 익혀두면 나중에 편하다.

2. 리서치 프로젝트 구조 — 6개월 뒤의 나를 위한 배려

대학원생이 가장 흔히 저지르는 실수: 모든 코드를 하나의 거대한 analysis.ipynb 노트북에 몰아넣는 것. 처음엔 편하지만, 3주만 지나면 셀 실행 순서가 꼬이고, 어떤 변수가 어디서 왔는지 모르게 되고, 재현이 불가능해진다. 해결책은 표준 프로젝트 레이아웃이다.

Definition 2.1 — 표준 리서치 프로젝트 레이아웃

데이터·로직·산출물을 물리적으로 분리하고, 데이터 흐름을 raw → interim → processed 한 방향으로 강제하는 디렉토리 구조.

# 권장 디렉토리 구조 (Good Research Code / Cookiecutter Data Science 계열)
kospi_value_factor/
├── data/
│   ├── raw/          # 원본. 절대 손대지 않는다 (read-only). git에 안 올림
│   ├── interim/      # 중간 산출물 (병합·필터링 단계)
│   └── processed/    # 분석 직전의 깨끗한 패널 (Parquet)
├── src/              # 재사용 가능한 파이썬 모듈 (import 대상)
│   ├── __init__.py
│   ├── config.py     # 경로·상수·시드 한 곳에
│   ├── data.py       # load_panel(), clean() ...
│   └── signals.py    # compute_zscore(), rank_quantile() ...
├── notebooks/        # 탐색용. 결과는 여기, 로직은 src로 승격
│   └── 01_value_eda.ipynb
├── reports/
│   └── figures/      # 논문·발표용 그림 (png/pdf)
├── tests/            # pytest — 시그널 함수 단위 테스트
├── environment.yml   # conda 환경 (버전 고정)
└── README.md         # "이걸 어떻게 재현하는가"를 3줄로

핵심 철학은 데이터 흐름의 단방향성이다. raw → interim → processed는 한 방향으로만 흐른다. raw/는 신성불가침 — 절대 덮어쓰지 않는다. 원본을 실수로 변형하면 되돌릴 수 없기 때문이다. 모든 변형은 새 파일로 processed/에 쓴다.

2.1 노트북 → 모듈 승격 규칙

노트북은 "생각하는 도구"이지 "저장하는 도구"가 아니다. 규칙: 한 번 더 쓸 것 같은 코드는 즉시 src/로 승격한다. 노트북에서는 import해서 호출만 한다.

# src/signals.py — 재사용 로직은 여기에
import pandas as pd

def compute_zscore(df: pd.DataFrame, col: str) -> pd.Series:
    """각 날짜(date) 안에서 횡단면 z-score. 패널 인덱스 (date, ticker) 가정."""
    g = df.groupby("date")[col]
    return (df[col] - g.transform("mean")) / g.transform("std")

# notebooks/01_value_eda.ipynb — 얇게 호출만
# from src.signals import compute_zscore
# panel["value_z"] = compute_zscore(panel, "book_to_market")
노트북 셀은 3~5줄로 유지된다. 로직은 전부 src/에서 테스트된 함수로 존재한다.

2.2 config: 단일 진실 공급원과 시드 고정

경로, 상수, 그리고 난수 시드는 코드 곳곳에 흩어지면 안 된다. 한 파일에 모은다. 특히 시드는 재현성의 핵심이다.

# src/config.py
from pathlib import Path

ROOT = Path(__file__).resolve().parents[1]
DATA_RAW = ROOT / "data" / "raw"
DATA_PROCESSED = ROOT / "data" / "processed"

SEED = 42                 # 모든 난수의 단일 시드
UNIVERSE = "KOSPI200"
REBALANCE = "ME"            # month-end 리밸런싱
N_QUANTILES = 5           # 5분위 포트폴리오

# 사용처에서:  rng = np.random.default_rng(config.SEED)

함정 — 시드를 안 고정하면 리서치가 거짓말을 한다: 부트스트랩, 교차검증 폴드 분할, 신경망 초기화, 몬테카를로 모두 난수를 쓴다. 시드를 고정하지 않으면 오늘 샤프 1.9, 내일 샤프 1.3이 나온다. 더 나쁜 것: 여러 시드를 몰래 돌려보고 "가장 좋은" 시드를 리포트하면 그것은 연구 부정(cherry-picking)이다. 시드는 config에 한 번 박아두고, 강건성 검증이 필요하면 "여러 시드에 대한 분포"를 전부 보고한다.

3. Git 연구 워크플로우 — 실험을 잃어버리지 않는 법

Git을 "백업 도구"로만 쓰면 절반만 쓰는 것이다. 리서처에게 Git은 실험 노트다. "저PBR 시그널을 넣었더니 샤프가 0.3 올랐다"는 사실을, 그 시점의 코드 상태와 함께 영구히 박제하는 도구다.

3.1 커밋 단위 — "하나의 논리적 변화"

좋은 커밋은 "하나의 논리적 변화"다. "저녁에 한 일 전부"를 한 커밋에 몰아넣지 않는다. 나중에 "어떤 변경이 성능을 올렸나"를 이분 탐색(git bisect)할 수 있어야 한다.

# 나쁜 커밋 — 무엇을 왜 바꿨는지 알 수 없음
git commit -m "update"

# 좋은 커밋 — 명령형, 변화의 '왜'가 드러남
git commit -m "feat: book-to-market 시그널에 횡단면 z-score 정규화 추가"
git commit -m "fix: 시그널 계산에서 shift(1) 누락으로 인한 lookahead 제거"
git commit -m "exp: 5분위→10분위로 변경, IC 0.03→0.04"

3.2 노트북 diff 문제 — nbstripout

노트북(.ipynb)은 JSON이고, 그 안에 셀 출력(그래프의 base64 이미지, 실행 횟수 카운터)까지 통째로 저장된다. 그래서 코드를 한 줄도 안 바꿔도 실행만 하면 파일이 바뀌고, git diff가 수천 줄의 알아볼 수 없는 JSON으로 오염된다.

4. NumPy 심화 — broadcasting, vectorization, 난수

Pandas의 밑에는 NumPy가 있다. 패널 데이터의 성능·정확성 문제는 결국 NumPy 수준에서 결정된다. 학부에서 np.array는 써봤을 테니, 여기서는 리서처가 반드시 정확히 알아야 하는 세 가지 — broadcasting 규칙, vectorization 성능, 재현 가능한 난수 — 에 집중한다.

4.1 Broadcasting 규칙 — 정확히

Broadcasting은 서로 다른 shape의 배열을 자동으로 확장해 원소별 연산을 하는 규칙이다. "대충 되겠지"가 아니라 규칙이 정확히 정해져 있다.

Definition 4.1 — Broadcasting 규칙

두 배열의 shape를 오른쪽 끝(뒤 차원)부터 비교한다. 각 차원 쌍이 (1) 두 값이 같거나 (2) 한쪽이 1이면 호환된다. 1인 쪽이 다른 쪽 크기로 "늘어난다(stretch)". 어느 쪽도 아니면 ValueError.

\[ (T \times N) \;\oplus\; (1 \times N) \;\rightarrow\; (T \times N), \qquad (T \times N) \;\oplus\; (T \times 1) \;\rightarrow\; (T \times N) \]

↑ "T개월 × N종목 수익률 행렬에 (1×N) 종목별 평균을 빼면 각 열에서 그 열 평균이 빠진다. (T×1) 날짜별 값을 빼면 각 행에서 그 행 값이 빠진다." 이 두 패턴이 금융 패널에서 시계열정규화·횡단면정규화의 핵심이다.

import numpy as np

# 24개월 × 4종목 수익률 행렬 (T×N)
rng = np.random.default_rng(42)
R = rng.normal(0.01, 0.05, size=(24, 4))   # shape (24, 4)

# (A) 횡단면 demean: 각 날짜(행)에서 그 날의 종목평균을 뺀다
row_mean = R.mean(axis=1, keepdims=True)   # shape (24, 1)
R_cs = R - row_mean                        # (24,4) - (24,1) → (24,4)
print("횡단면 demean 후 각 행 합 ≈ 0:", np.round(R_cs.sum(axis=1)[:3], 6))

# (B) 종목별 표준화: 각 종목(열)을 그 종목의 평균/표준편차로 z-score
col_mean = R.mean(axis=0, keepdims=True)   # shape (1, 4)
col_std  = R.std(axis=0, keepdims=True)    # shape (1, 4)
R_z = (R - col_mean) / col_std             # (24,4) - (1,4) → (24,4)
print("종목별 z-score 후 각 열 평균 ≈ 0:", np.round(R_z.mean(axis=0), 6))
Output: 횡단면 demean 후 각 행 합 ≈ 0: [ 0. -0. 0.] 종목별 z-score 후 각 열 평균 ≈ 0: [ 0. 0. -0. 0.]

함정 — keepdims를 빼먹으면 축이 어긋난다: R.mean(axis=1)은 shape (24,)를 반환한다. 이걸 R(24,4)에서 빼면 broadcasting 규칙상 (24,)는 (1,24)로 해석되어 (24,4)와 뒤 차원(4 vs 24)이 안 맞아 에러가 나거나, 더 나쁘게는 축이 우연히 맞으면 조용히 잘못된 방향으로 빼진다. 항상 keepdims=True로 축을 명시하라. 금융 패널에서 "행 방향(횡단면)인지 열 방향(시계열)인지"를 헷갈리면 정규화가 통째로 틀린다.

4.2 Vectorization vs 루프 — 성능 실측

"파이썬 for 루프는 느리다"는 말은 들어봤을 것이다. 얼마나 느린지 금융 예제로 실측하자. 100만 개 수익률의 로그수익률 변환을 루프 vs 벡터화로.

import numpy as np, time

rng = np.random.default_rng(0)
r = rng.normal(0.0004, 0.012, size=1_000_000)   # 100만 개 일간 수익률

# (A) 순수 파이썬 루프
t0 = time.perf_counter()
out_loop = [np.log(1 + x) for x in r]
t_loop = time.perf_counter() - t0

# (B) 벡터화 — 배열 전체에 한 번에
t0 = time.perf_counter()
out_vec = np.log1p(r)                # log(1+x)를 정밀하게
t_vec = time.perf_counter() - t0

print(f"루프  : {t_loop*1000:7.1f} ms")
print(f"벡터화: {t_vec*1000:7.1f} ms")
print(f"속도 향상: {t_loop/t_vec:.0f}배")
Output: 루프 : 612.4 ms 벡터화: 6.8 ms 속도 향상: 90배

벡터화가 빠른 이유는 마법이 아니다. 루프는 파이썬 인터프리터가 원소 100만 번을 하나씩 해석하지만, np.log1p는 그 반복을 C 레벨에서 SIMD로 처리한다. 리서치에서 이 차이는 "커피 마시고 오면 끝"과 "화면 보며 기다림"의 차이다. 그리고 np.log1p(x)는 np.log(1+x)보다 수치적으로 더 정확하다(작은 x에서 자릿수 손실 방지).

4.3 einsum — 헷갈리는 텐서 연산을 명시적으로

포트폴리오 분산 w^T Σ w, 배치 행렬곱 같은 연산은 einsum으로 인덱스를 명시해 쓰면 실수가 준다. R11의 리스크 계산에서 유용하다.

import numpy as np

w = np.array([0.5, 0.3, 0.2])
Sigma = np.array([[0.04,0.006,0.002],
                  [0.006,0.01,0.004],
                  [0.002,0.004,0.005]])

# 이차형식 wᵀΣw — 두 가지 동치 표현
v1 = w @ Sigma @ w
v2 = np.einsum("i,ij,j->", w, Sigma, w)   # "i,ij,j → 스칼라"
print(f"w@Σ@w   = {v1:.6f}")
print(f"einsum  = {v2:.6f}")

# einsum의 진가: 여러 날짜의 포트폴리오 수익률을 한 번에
W = np.array([[0.5,0.3,0.2],[0.4,0.4,0.2]])  # 2일치 비중 (2×3)
Rt = np.array([[0.01,0.02,-0.01],[0.00,-0.01,0.03]]) # 2일치 수익 (2×3)
port_ret = np.einsum("ti,ti->t", W, Rt)   # 날짜별 wᵀr
print(f"일별 포트폴리오 수익: {np.round(port_ret,4)}")
Output: w@Σ@w = 0.013540 einsum = 0.013540 일별 포트폴리오 수익: [0.006 0.002]

rng_a = np.random.default_rng(42)

returns = rng_a.normal(0.008, 0.05, 60)
idx = rng_a.integers(0, len(returns), size=len(returns))  # 복원추출 인덱스
boot_sample = returns[idx]
print(f"원본 평균: {returns.mean():.4f}, 부트스트랩 평균: {boot_sample.mean():.4f}")
Output: rng_a: [ 0.3047 -1.0399 0.7504] rng_b: [ 0.3047 -1.0399 0.7504] 원본 평균: 0.0079, 부트스트랩 평균: 0.0112

함정 — 부동소수점은 결합법칙을 지키지 않는다: 수학에서 \((a+b)+c = a+(b+c)\)이지만 float64에서는 아니다. 큰 값과 작은 값을 더하면 작은 값의 하위 비트가 소실된다(catastrophic cancellation). 그래서 100만 개 수익률의 합은 np.sum(쌍대합, pairwise summation을 씀)이 순진한 루프 덧셈보다 정확하다. 또 0.1 + 0.2 == 0.3은 False다. 두 실수의 동등 비교는 항상 np.isclose를 써라. 백테스트에서 "비중 합이 정확히 1인가"를 == 1.0으로 검사하면 언젠가 반드시 터진다.

5. Pandas 심화 I: Index가 전부다

Pandas 초보와 숙련자를 가르는 단 하나의 개념: Index. 초보는 Index를 "행 번호" 정도로 여기고 reset_index()를 남발한다. 숙련자는 Index를 데이터의 좌표계로 설계한다. 금융 패널 데이터의 자연스러운 좌표계는 (date, ticker)다.

5.1 MultiIndex로 패널 데이터 표현하기

Definition 5.1 — 패널 데이터 (Panel Data)

패널 데이터는 여러 개체(ticker)를 여러 시점(date)에 걸쳐 관측한 데이터다. 자연스러운 인덱스는 (date, ticker) 2차원 MultiIndex다.

\[ x_{i,t} \;\;\Leftrightarrow\;\; \texttt{panel.loc[(t,\ i),\ col]} \]

↑ "종목 i의 시점 t 값 \(x_{i,t}\)"라는 수식이 곧 (date, ticker) MultiIndex의 한 원소다. 계량경제 교과서의 \(i, t\) 첨자가 그대로 pandas 인덱스가 된다.

import pandas as pd
import numpy as np

# KOSPI200 스타일 가짜 패널: 3종목 × 4개월
dates = pd.to_datetime(["2024-01-31","2024-02-29","2024-03-31","2024-04-30"])
tickers = ["005930", "000660", "035420"]   # 삼성전자·SK하이닉스·NAVER

print(panel.head(6))
print("\nindex names:", panel.index.names)

5.2 alignment — Pandas의 진짜 마법

Pandas가 NumPy와 결정적으로 다른 점: 연산할 때 인덱스를 자동으로 정렬(align)한다. 두 Series를 더하면 위치가 아니라 라벨이 맞는 것끼리 더해진다.

import pandas as pd

# 순서가 다르고, 한쪽에만 있는 종목이 있어도...
signal = pd.Series({"005930": 1.2, "000660": -0.5, "035420": 0.8})
weight = pd.Series({"035420": 0.3, "005930": 0.5, "051910": 0.2})  # 051910는 signal에 없음

aligned = signal * weight   # 라벨 기준 정렬 후 곱
print(aligned)
Output: 000660 NaN 005930 0.60 035420 0.24 051910 NaN dtype: float64

위 결과에서 005930은 양쪽에 있으니 1.2 × 0.5 = 0.60. 그러나 000660(weight에 없음)과 051910(signal에 없음)은 짝이 없어 NaN이 된다. 이것이 축복이자 저주다. 축복: 위치를 안 맞춰도 라벨로 알아서 정렬된다. 저주: 무심코 NaN이 퍼진다.

함정 — 정렬 자동화가 조용히 데이터를 삼킨다: 시그널과 다음 달 수익률을 곱해 팩터 수익을 계산할 때, 두 Series의 종목 집합이 다르면(상장폐지·신규상장) 겹치지 않는 종목이 NaN이 되어 조용히 사라진다. 이걸 모르고 .sum()하면 표본이 매달 다른 종목 수로 계산돼 결과가 왜곡된다. 항상 연산 전후로 len과 isna().sum()을 찍어 "몇 개가 정렬로 탈락했는지" 확인하라. 이것은 R6 팩터 IC 계산에서 반복적으로 무는 함정이다.

6.3 merge vs merge_asof — 시점 정렬 병합

가격 데이터(일간)에 재무 데이터(분기·비정기 공시)를 붙일 때, 날짜가 정확히 안 맞는다. merge는 정확히 일치하는 키만 붙이지만, merge_asof는 "가장 최근의 과거 값"을 붙인다. 이것이 금융에서 point-in-time 데이터를 만드는 핵심 도구다.

7.2 shift와 lookahead — 미래를 훔치는 한 줄

이 라운드에서 가장 중요한 코드다. 시그널로 다음 기간 수익률을 예측하려면, 시그널은 반드시 수익률보다 먼저 알려진 값이어야 한다. shift(1)이 그 시간 정렬을 보장한다.

Definition 7.1 — 예측의 시간 정렬

\[ \underbrace{r_{t+1}}_{\text{예측 대상}} \;=\; f\big(\underbrace{s_{t}}_{\text{t시점까지 알려진 시그널}}\big) + \epsilon_{t+1} \]

↑ "t+1의 수익률은 t시점까지 알려진 시그널로만 예측해야 한다." 만약 \(r_{t+1}\)을 \(s_{t+1}\)로 예측하면 미래 정보로 미래를 맞히는 것 — lookahead bias. pandas에서 시그널을 shift(1)하면 "t의 시그널을 t+1의 수익률과 짝지어" 이 정렬을 강제한다.

import pandas as pd, numpy as np

rng = np.random.default_rng(3)
m = pd.DataFrame(index=pd.date_range("2024-01-31", periods=6, freq="ME"))
m["ret"]    = rng.normal(0.01, 0.05, 6)
m["signal"] = rng.normal(0, 1, 6)     # 그 달 말에 계산되는 시그널

# ✗ 틀린 방법: 같은 달 시그널로 같은 달 수익률 설명 → LOOKAHEAD
wrong = (m["signal"] * m["ret"]).mean()

# ✓ 올바른 방법: 지난 달 시그널로 이번 달 수익률 (shift로 정렬)
m["signal_lag"] = m["signal"].shift(1)   # t-1의 시그널을 t로 밀어줌
correct = (m["signal_lag"] * m["ret"]).mean()   # 첫 행은 NaN → 자동 제외

print(m.round(4))
print(f"\n✗ lookahead(틀림): {wrong:+.5f}")
print(f"✓ shift(1)(맞음): {correct:+.5f}")
Output: ret signal signal_lag 2024-01-31 0.0705 1.1530 NaN 2024-02-29 -0.0340 -0.2287 1.1530 2024-03-31 0.0466 0.4746 -0.2287 2024-04-30 0.0231 -0.5382 0.4746 2024-05-31 -0.0093 -0.4438 -0.5382 2024-06-30 0.0518 0.1352 -0.4438 ✗ lookahead(틀림): +0.02015 ✓ shift(1)(맞음): -0.00379

함정 — 이 한 줄이 백테스트의 생사를 가른다: 위 출력에서 lookahead 버전은 +0.02015로 "시그널이 수익을 예측한다"고 착각하게 만들지만, 올바른 shift(1) 버전은 -0.00379로 사실상 예측력이 없다. 같은 달 시그널로 같은 달 수익률을 "예측"하면 대부분의 시그널이 마법처럼 작동하는 것처럼 보인다 — 시그널과 수익률이 동시점 상관을 가지기 때문이다. 백테스트가 너무 좋으면 가장 먼저 shift를 의심하라. 실무에서는 시그널 계산 시점과 거래 체결 시점 사이의 지연(공시 지연, 리밸런싱 시차)까지 고려해 shift(1) 또는 그 이상을 적용한다.

7.3 rolling과 expanding

from numba import njit
import numpy as np

@njit   # 파이썬 함수를 기계어로 JIT 컴파일
def max_drawdown(cum: np.ndarray) -> float:
    peak = cum[0]; mdd = 0.0
    for x in cum:
        if x > peak: peak = x
        dd = x / peak - 1.0
        if dd < mdd: mdd = dd
    return mdd

rng = np.random.default_rng(0)
cum = np.cumprod(1 + rng.normal(0.0005, 0.02, 2520))  # 10년 일간
print(f"최대낙폭(MDD): {max_drawdown(cum):.2%}")

9. 데이터 저장 — CSV의 함정과 Parquet

대학원생이 데이터를 to_csv로 저장하는 순간 세 가지 재앙이 시작된다: dtype 소실, 인코딩 깨짐, 정밀도 손실. 리서치 데이터는 Parquet으로 저장해야 한다.

9.1 CSV의 세 가지 함정

함정 — CSV는 "타입 없는 텍스트"다:

  • dtype 소실: CSV는 모든 것을 문자열로 저장한다. 다시 읽으면 category는 object로, datetime은 문자열로 돌아가 매번 parse_dates를 지정해야 한다. 종목코드 "005930"은 정수 5930으로 읽혀 앞의 0이 사라진다.
  • 인코딩: 한글 종목명이 있으면 Windows(cp949)와 Mac(utf-8) 사이에서 깨진다. Excel로 열었다 저장하면 인코딩이 바뀐다.
  • 정밀도: float64를 텍스트로 쓰면 반올림되어 마지막 자릿수가 손실될 수 있다. 다시 읽은 값이 원본과 !=가 된다.

9.3 캐싱 데코레이터 — 비싼 계산을 한 번만

데이터 로드·정제가 느리면 노트북을 돌릴 때마다 기다린다. 간단한 캐싱 데코레이터로 "처음 한 번만 계산하고, 이후엔 Parquet에서 읽기"를 자동화한다.

import pandas as pd
from pathlib import Path
from functools import wraps

def parquet_cache(path: str):
    """반환된 DataFrame을 Parquet으로 캐시. 파일 있으면 바로 읽음."""
    def deco(func):
        @wraps(func)
        def wrapper(*args, **kw):
            p = Path(path)
            if p.exists():
                print(f"[cache] {path} 에서 로드")
                return pd.read_parquet(p)
            print(f"[compute] 계산 후 {path} 에 저장")
            df = func(*args, **kw)
            df.to_parquet(p)
            return df
        return wrapper
    return deco

@parquet_cache("data/processed/clean_panel.parquet")
def load_clean_panel():
    # ... 느린 로드 + 정제 ...
    return pd.DataFrame({"ret": [0.01, 0.02]})

df = load_clean_panel()   # 1회차: compute / 2회차부터: cache
Output: [compute] 계산 후 data/processed/clean_panel.parquet 에 저장 # (재실행 시) [cache] data/processed/clean_panel.parquet 에서 로드

캐시의 위험과 규율: 캐시는 편하지만 "코드를 바꿨는데 옛 캐시를 읽는" 사고를 부른다. 실무에서는 캐시 키에 입력 데이터 해시나 코드 버전을 넣거나, 데이터 갱신 시 캐시를 명시적으로 지운다. 이것도 Ch.2의 "raw는 불변, processed는 재생성 가능" 원칙의 연장이다 — 캐시는 언제든 지워도 코드로 복원돼야 한다.

10. 실습: 가짜 KOSPI200 패널로 z-score 파이프라인 구축

10.1 가짜 패널 생성

import pandas as pd, numpy as np

SEED = 42                                # config.SEED (재현성)
rng = np.random.default_rng(SEED)

# 20종목 × 36개월 KOSPI200 스타일 패널
dates   = pd.date_range("2021-01-31", periods=36, freq="ME")
tickers = [f"A{i:05d}" for i in rng.choice(range(100000), 20, replace=False)]

idx = pd.MultiIndex.from_product([dates, tickers], names=["date","ticker"])
n = len(idx)

# 공통 시장 팩터 + 종목 고유 노이즈 (상관구조 부여)
mkt = rng.normal(0.008, 0.045, len(dates))
mkt_rep = np.repeat(mkt, len(tickers))
beta = np.tile(rng.uniform(0.6, 1.4, len(tickers)), len(dates))

panel = pd.DataFrame({
    "ret": (beta * mkt_rep + rng.normal(0, 0.03, n)).astype("float32"),
    "bm":  rng.lognormal(0, 0.4, n).astype("float32"),   # book-to-market
}, index=idx).sort_index()

print(f"패널 shape: {panel.shape}, 메모리: {panel.memory_usage(deep=True).sum()/1e3:.1f} KB")
print(panel.head(3))

10.3 groupby-transform z-score + shift 정렬 (핵심)

# === 파이프라인의 심장: 횡단면 z-score → 다음 달 수익률과 정렬 ===

# (1) 각 날짜(횡단면) 안에서 bm 시그널을 z-score 표준화
g = panel.groupby("date")["bm"]
panel["bm_z"] = (panel["bm"] - g.transform("mean")) / g.transform("std")

# (2) shift(1): t월의 시그널을 t+1월 수익률과 짝짓는다 (LOOKAHEAD 방지!)
#     ticker별로 시계열을 밀어야 하므로 groupby('ticker')
panel["bm_z_lag"] = panel.groupby("ticker")["bm_z"].shift(1)

# (3) 지난달 시그널 z-score와 이번달 수익률의 횡단면 상관 = IC
def cross_sec_ic(df):
    d = df.dropna(subset=["bm_z_lag","ret"])
    if len(d) < 3: return np.nan
    return np.corrcoef(d["bm_z_lag"], d["ret"])[0,1]

ic = panel.groupby("date").apply(cross_sec_ic, include_groups=False)
print(f"평균 IC (shift 적용): {ic.mean():+.4f}")
print(f"IC 표준편차: {ic.std():.4f}")
print(f"IR (IC/std): {ic.mean()/ic.std():+.3f}")

# 비교: shift를 빼먹은 lookahead 버전 (동시점) — 항상 달라 보인다
def ic_lookahead(df):
    d = df.dropna(subset=["bm_z","ret"])
    return np.corrcoef(d["bm_z"], d["ret"])[0,1]
ic_bad = panel.groupby("date").apply(ic_lookahead, include_groups=False)
print(f"\n✗ lookahead 평균 IC: {ic_bad.mean():+.4f}  ← shift 없으면 왜곡")
Output: 평균 IC (shift 적용): +0.0087 IC 표준편차: 0.2140 IR (IC/std): +0.041 ✗ lookahead 평균 IC: -0.0153 ← shift 없으면 왜곡

파이프라인 완성 — 이것이 R5의 뼈대다: (1) groupby("date").transform으로 횡단면 z-score, (2) groupby("ticker").shift(1)로 시간 정렬(lookahead 방지), (3) 날짜별 횡단면 상관으로 IC(정보계수). R5에서는 여기에 분위 포트폴리오 구성과 t-검정이 추가될 뿐, 전처리 골격은 완전히 동일하다. 지금 이 코드가 손에 익으면 R5는 절반은 끝난 것이다.

Q8. (핵심) 시그널로 다음 달 수익률을 예측할 때 signal.shift(1)이 왜 필수인가? 이를 빼면 어떤 착시가 생기나?
t+1의 수익률은 t시점까지 알려진 시그널로만 예측해야 한다(\(r_{t+1}=f(s_t)\)). shift(1)은 t의 시그널을 t+1 수익률과 짝지어 이 시간 정렬을 강제한다. 빼먹으면 같은 시점의 시그널과 수익률을 곱하게 되는데, 둘은 동시점 상관을 가지므로 대부분의 시그널이 마법처럼 예측력이 있는 것처럼 보인다. 본문 예에서 lookahead IC는 shift(1) 후엔 0 근처로 무너진다. 백테스트가 너무 좋으면 가장 먼저 shift를 의심하라.
Q9. 대용량 패널을 float32·category로 다이어트할 때의 이득과, 절대 float32로 하면 안 되는 계산은?
이득: float64→float32는 메모리 절반, 반복 문자열(종목코드)→category는 대폭 절감(본문 예 약 92%). 그러나 float32는 유효숫자 약 7자리라, 누적곱(복리 수익 곡선)이나 공분산 역행렬처럼 오차가 누적·증폭되는 계산은 float64로 해야 한다. 원칙은 "저장은 float32, 계산은 float64".
Q10. 리서치 데이터를 to_csv가 아니라 Parquet으로 저장해야 하는 세 가지 이유는?
(1) dtype 소실: CSV는 모든 것을 문자열로 저장 — datetime·category가 풀리고 종목코드 "005930"의 앞 0이 사라진다. (2) 인코딩: 한글이 cp949/utf-8 사이에서 깨진다. (3) 정밀도: float를 텍스트로 쓰면 마지막 자릿수가 손실될 수 있다. Parquet은 타입·MultiIndex·정밀도를 완벽 보존하고, 압축과 컬럼 단위 읽기까지 지원한다. Feather는 빠른 임시 캐시, Pickle은 버전 의존적이라 비추천.
